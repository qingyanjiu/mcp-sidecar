### SEC-01 fastjson 全局 AutoType + 远端响应反序列化

**位置**

- `src/main/java/com/hx/mcpsidecar/config/CustomRedisConfig.java:26`
- `src/main/java/com/hx/mcpsidecar/utils/redis/FastJsonRedisSerializer.java:31,40`
- `src/main/java/com/hx/mcpsidecar/service/mcp/ragflow/RagflowApiClient.java:148`
- `src/main/java/com/hx/mcpsidecar/service/mcp/platform/PlatformPersonStatusMcp.java:45`

**现状（修复前）**

`CustomRedisConfig` 在 Bean 初始化时对 JVM 全局调用
`ParserConfig.getGlobalInstance().setAutoTypeSupport(true)`。同时 fastjson 版本为 1.2.83，
受 CVE-2026-16723 影响（1.2.68–1.2.83，Spring Boot fat-jar 场景可 RCE，已有公开利用）。
项目正好是 fat-jar，且 RAGFlow、Platform 响应均通过明文 HTTP 获取。

**风险**

RAGFlow/Platform 或中间网络设备被控后，返回恶意 JSON 即可触发反序列化 RCE。
即使 Redis 当前未被业务调用，`setAutoTypeSupport(true)` 是全局配置，影响所有 fastjson 解析点。

**修复**

1. 删除 `setAutoTypeSupport(true)`；如必须保留，改为 `setSafeMode(true)`。
2. RAGFlow/Platform 响应改用 Jackson 或明确的 DTO，不使用 `JSON.parseObject` 解析外部数据。
3. fastjson 升级到 fastjson2 2.0.58+；短期至少换 `1.2.83_noneautotype`。
4. `FastJsonRedisSerializer` 若确认 Redis 未使用，直接删除相关配置类。

**验收**：全局搜索无 `setAutoTypeSupport(true)`；外部 HTTP 响应无 fastjson 解析；依赖树无 1.2.83。

**修复记录（2026-11-17，已完成）**

**修改过程**

1. `CustomRedisConfig`：删除 `ParserConfig.getGlobalInstance().setAutoTypeSupport(true)`。这是 JVM 全局开关，本项目的 Redis 也没有业务使用，没有保留理由。
2. `RagflowApiClient`：RAGFlow 响应原先用 `JSON.parseObject` 解析，改为 `ObjectMapper.readValue(..., Map.class)`，再包装成只读 `JSONObject` 供现有代码取值；空响应直接抛错，避免后续 NPE。
3. `PlatformPersonStatusMcp`：平台响应已经是由 RestTemplate/Jackson 解析出的 `Map`，删除 fastjson 往返转换，直接按字段读取，并补 `toInteger` 兼容 Number/字符串。
4. 删除未被引用的 `utils/redis/FastJsonRedisSerializer`，该实现同时使用 `WriteClassName` 和 `parseObject`，属于多态反序列化入口。
5. 依赖升级：`pom.xml` 将 `com.alibaba:fastjson:1.2.83` 替换为 `com.alibaba.fastjson2:fastjson2:2.0.66`；主代码与测试共 19 个文件的 import 从 `com.alibaba.fastjson.*` 改为 `com.alibaba.fastjson2.*`。现有用法只有 `JSON.toJSONString`、`JSONObject`、`JSONArray` 等序列化 API，fastjson2 保持兼容，业务逻辑无需改动。
6. 回归与制品核验：
   - `mvn -DskipTests compile`、`mvn -DskipTests package` 成功；
   - 定向 24 个用例通过，含 `McpTest`（平台工具注册/调用）；
   - `mvn dependency:tree -Dincludes=com.alibaba:fastjson,com.alibaba.fastjson2:fastjson2` 只输出 `com.alibaba.fastjson2:fastjson2:jar:2.0.66:compile`；
   - `unzip -l target/mcp-sidecar.jar | grep -i fastjson` 只输出 `BOOT-INF/lib/fastjson2-2.0.66.jar`。

**核心逻辑**

- fastjson 的风险不在“解析 JSON”本身，而在 AutoType 允许 JSON 里的 `@type` 决定实例化哪个类。只要全局 AutoType 打开，任何解析远端 JSON 的地方都可能成为 RCE 入口。
- 本项目的做法是**彻底取消多态反序列化**：外部数据只解析为 `Map`/明确 DTO，不再根据 JSON 内容选择类。这样即使依赖还在，也不能通过 `@type` 触发利用链。
- 1.2.83 的 CVE-2026-16723 是 fat-jar 场景下的已知 RCE，仅靠“不再调用 parseObject”仍会把有漏洞的类留在制品里；升级到 fastjson2 后该版本被彻底移出依赖树和成品 jar，攻击面才真正关闭。
- fastjson2 的 AutoType 默认关闭，且项目没有重新打开；现有用途只剩序列化，序列化不读取 `@type`，风险远低于反序列化。

**验收结果**

- 全局搜索无 `setAutoTypeSupport`，外部 HTTP 响应无 `parseObject`/`JSON.parse`。
- 依赖树与 `target/mcp-sidecar.jar` 均只含 fastjson2 2.0.66，无 fastjson 1.2.83。
- 平台、RAGFlow、MCP 工具定向回归通过；全量测试仅剩与本条无关的 `MockData*` 既有失败。

### SEC-02 Platform 服务账号硬编码，凭据进入 URL

**位置**

- `src/main/java/com/hx/mcpsidecar/service/mcp/platform/PlatformApiCallServiceImpl.java:59-63,74,91`
- `.claude/worktrees/readme-update/src/main/java/com/hx/mcpsidecar/service/mcp/platform/PlatformApiCallServiceImpl.java`（同内容副本）

**现状**

用户名、密码、验证码均为 `<已硬编码>`；登录时把凭据拼到
`baseUrl + "/login?" + toQueryString(params)`；`getLoginInfo` 也走 HTTP。
`getLoginInfo` 失败时回退明文登录。

**风险**

能读源码或 jar 的人可直接获得平台高权限账号；凭据出现在 URL query，会进入
Nginx/网关/代理访问日志和浏览器历史；HTTP 传输可被同网段嗅探。

**修复**

1. 立即轮换该平台账号及验证码配置。
2. 凭据改为环境变量/密钥管理注入，代码中只保留占位符。
3. 登录参数改 POST body；强制 HTTPS；平台未启用 RSA 时直接失败，不回退明文。
4. 删除 worktree 中的重复副本，避免再次提交。

**验收**：源码与 jar 中搜索不到该用户名/口令；登录请求不再含 query 凭据。

**修复记录（2026-11-17，部分完成）**

**修改过程**

1. 新增项目根目录 `.env`（已被 `.gitignore` 忽略），集中保存平台账号、验证码、RAGFlow、Redis、数据库、SSL、Kafka 等真实值；同时提供内容为空的 `.env.example` 作为模板。
2. 本地启动：`application.yml` 增加 `spring.config.import: optional:file:./.env[.properties]`，项目从根目录 `.env` 读取配置。
3. Docker 启动：Compose 自动读取同目录 `.env`，并通过 `mcp-sidecar.environment` 显式映射 `PLATFORM_LOGIN_USERNAME` / `PLATFORM_LOGIN_PASSWORD` / `PLATFORM_LOGIN_TYPE` / `PLATFORM_CAPTCHA_ID` / `PLATFORM_CAPTCHA_CODE` / `PLATFORM_ALLOW_PLAINTEXT_LOGIN` 等变量进入容器。
4. `PlatformApiCallServiceImpl` 删除硬编码凭据，改为 `@Value` 注入：
   - `mcp.servers.platform.login-username`、`login-password`、`login-type`、`captcha-id`、`captcha-code`；
   - `mcp.servers.platform.allow-plaintext-login`，默认 `false`。
5. 登录请求从 `GET /login?username=...&password=...` 改为 `POST /login`，参数放在 `application/x-www-form-urlencoded` body；URL 中不再出现账号、口令、验证码。
6. 保留 RSA 公钥加密路径；拿不到公钥或请求异常时不再静默回退明文，而是抛错。只有显式设置 `allow-plaintext-login=true` 才允许明文提交，并在日志中打 WARN。
7. 测试同步：
   - `PlatformApiCallServiceImplTest` 改为断言 POST body 中的参数，并新增“默认拒绝明文登录”用例；
   - `McpTest` 集成用例从环境变量读取账号，未设置时 `assumeTrue` 跳过，不在测试代码中保存真实凭据。

**核心逻辑**

- 硬编码凭据的风险有两层：源码/jar 可读，以及凭据拼进 URL 后进入代理、网关、访问日志。只做“搬到配置文件”仍会随 jar/仓库泄露，所以真实值必须放在**未跟踪的运行态文件**里，代码和 tracked 配置只保留占位符。
- 登录参数改 POST body 是为了让凭据不进入 URL；但 HTTP 本身仍是明文。当前按内网部署接受该风险（SEC-17），本条不把 TLS 算作已完成。
- 明文回退默认关闭，是因为“RSA 失败就退回明文”会把一次配置/网络故障变成长期明文传输；显式开关把它变成一次可见的运维决策。

**剩余动作**

1. 轮换该平台账号及验证码配置，按“已泄露”处理；轮换后更新 `.env`。
2. sidecar 与平台后端之间按内网/专线信任处理（SEC-17 已按内网部署接受风险）；若该链路跨不可信网络，再启用入口 TLS。
3. 确认 `.env` 未进入 Docker 构建上下文、镜像、备份和日志；`.dockerignore` 已排除。
4. 平台 RSA 验证通过后，把 `.env` 中的 `PLATFORM_ALLOW_PLAINTEXT_LOGIN` 改为 `false`（当前为兼容联调保持 `true`）。
5. 本地还有一个未清理的 worktree：`.claude/worktrees/readme-update`（分支 `worktree-readme-update`），其中旧版 `PlatformApiCallServiceImpl` 仍保留凭据拼 URL 的写法。它不在当前 Git 分支中，但会随本地备份/整目录打包泄露；确认不需要后执行 `git worktree remove .claude/worktrees/readme-update`。

**验收结果**

### SEC-06 MCP Java SDK 请求体无上限 DoS

**位置**：`pom.xml` 中 `io.modelcontextprotocol.sdk:mcp-core:0.17.0`

**现状**：CVE-2026-108395，请求体无大小限制可导致堆耗尽。

**修复**：升级到 0.18.4 / 1.1.4 / 2.0.1+，与 Spring AI 升级一并做；在 2223 前置层加请求体大小限制。

**验收**：发送超大 initialize 请求被 413/连接拒绝，进程内存不持续增长。

**修复记录（2026-11-17，已完成）**

**修改过程**

1. `pom.xml` 增加 `mcp.sdk.version=0.18.4`，先导入 `io.modelcontextprotocol.sdk:mcp-bom`，再导入 `spring-ai-bom`，确保 MCP 传递依赖被提升到 0.18.4。
2. Spring AI 从 1.1.2 升到 1.1.8：0.18.4 删除了 `McpJsonMapper.createDefault()`，1.1.2 运行时直接 `NoSuchMethodError`；1.1.8 编译时已适配 0.18.x。
3. Spring Boot 从 3.2.3 升到 3.5.15（同时解决 SEC-12）；目标 JDK 仍为 17。
4. 新增 `McpRequestSizeLimitFilter`，只作用于 2223 的 `/mcp/**`：
   - 有 `Content-Length` 时先比较，超过 `mcp.max-request-size`（默认 1 MiB）直接 413，不读 body；
   - chunked 没有 `Content-Length`，用计数的 `ServletInputStream` 边读边限制，超限抛内部异常并返回 413；
   - 2222 的 `/llm/**`、`/ws/**` 与 9970 不受影响。
5. `application.yml` 增加 `mcp.max-request-size: 1048576`，`McpSidecarBootstrap` 静态块设置 `io.modelcontextprotocol.strictToolNameValidation=false`，兼容历史工具名前缀（如 `device:`、`device_query:`）。
6. 新增 `McpRequestSizeLimitFilterTest` 4 个用例：Content-Length 超限、正常请求、chunked 超限、非内网口/非 MCP 路径放行。

**核心逻辑**

- CVE-2026-108395 的根因是“先把整个请求体读进内存，再判断/解析”，所以只升级 SDK 仍不够：本服务用的是 `WebMvcStreamableServerTransportProvider`，它没有暴露 `maxRequestSize` 配置，Tomcat 的 `maxPostSize` 又只约束 form 表单。必须在 Servlet 层对 JSON body 加硬上限。
- 只按 `Content-Length` 判断可以被 chunked 绕过，因此没有长度时必须限制实际读取字节数；两条路径都在“超限的第一个字节”中止，不把后面的数据继续读进堆。
- 1 MiB 对 MCP 的 initialize / tools/call 足够大；正常工具参数都是短 JSON，调大只会扩大单请求可占用的内存。
- 工具名兼容开关是“保持客户端兼容”的临时措施，不涉及安全边界：工具名由服务端 `@McpTool` 定义，客户端不能自定义工具名。后续可批量把 `:` 改成 `.` 并同步 agentic-app 配置，再删除该开关。

**遗留**

- 工具名仍不符合 MCP 规范字符集，启动时会有 WARN；这是兼容性债，不是运行时漏洞。
- 升级后的完整回归只覆盖非 MockData 用例；`MockDataAspect*` 的既有失败与本次升级无关，需在 mock 分支单独修。

**验收**：依赖树为 MCP SDK 0.18.4 / Spring AI 1.1.8 / Boot 3.5.15；4 个大小限制用例通过；上下文冒烟通过；定向 35 个用例 34 通过、1 跳过；`mvn -DskipTests clean package` 成功。

### SEC-07 `/ws/scene` 无鉴权，会话可被顶替/伪造

**位置**

- `src/main/java/com/hx/mcpsidecar/config/ws/WsConfig.java:34-35`
- `src/main/java/com/hx/mcpsidecar/scene/SceneWebSocketHandler.java`
- `src/main/java/com/hx/mcpsidecar/scene/SceneSessionRegistry.java`
- `src/main/java/com/hx/mcpsidecar/scene/SceneProperties.java`（`singleSessionFallback` 默认 true）

**现状**

该端点未挂任何拦截器；`hello` 只要求客户端自报 `sessionId`；同 sessionId 新连接会顶掉旧连接，
并把 pending 动作重发给新连接；会话数量无上限，仅 30 分钟空闲回收。
本机实测：不带任何 token 发送 `hello` 即被接受并注册。

**风险**

知道/猜到 sessionId 即可顶替真实页面、读取动作参数、伪造 `action_result`；
随机 sessionId 可无限建会话造成内存 DoS。

**修复**

1. `hello` 增加短期签名或绑定 userId/token，服务端校验后才注册。
2. 限制单 IP 连接数、全局会话数；同 sessionId 顶替需二次确认或拒绝。
3. 校验 Origin；对 `action_result` 校验来源连接。

**验收**：无凭证 `hello` 被拒绝；伪造 sessionId 无法接收动作；压测下会话数有上限。

**修复记录（2026-11-17，已完成）**

**修改过程**

1. `WsConfig` 的 `/ws/scene` 注册增加 `AuthHandshakeInterceptor`：从 `Authorization` 头或 `?token=` 提取平台 token，从 query 提取 `userId`。
2. `SceneWebSocketHandler.onHello` 增加鉴权：
   - 没有 token 直接以 `1003 NOT_ACCEPTABLE` 关闭；
   - token 支持 `Bearer ` 前缀；
   - userId 可来自 query 或 hello 帧，两处都填时必须一致；
   - 调用 `IAuthService.validateToken(token, userId)` 走平台校验，失败关闭连接；
   - 平台调用异常时返回 `1011 SERVER_ERROR`，不把异常细节回给客户端。
3. `SceneSessionRegistry` 把 sessionId 绑定到 userId：
   - 已存在 sessionId 的 owner 与当前 userId 不一致时返回 `USER_MISMATCH`，拒绝顶替；
   - 同一用户重连仍然复用会话、顶掉旧 socket；
   - 新增 `scene.max-sessions`（默认 1000），达到上限后拒绝新 sessionId，已有 sessionId 重连不受影响。
4. `SceneProperties` 增加 `maxSessions`；`SceneSession` 增加 `isOwnedByDifferentUser`。
5. 新增 `SceneWebSocketHandlerTest` 8 个用例、`SceneSessionRegistryTest` 3 个用例。

**核心逻辑**

- 之前“知道 sessionId 就能顶替”的根因是只把 sessionId 当路由键，没有身份概念。现在连接先过平台 token 校验，再把 sessionId 归属到 userId；后续 `action_result` 只认当前已绑定 socket 上的 sessionId，其他用户无法接管。
- token 必须在 hello 时校验，而不是只在握手时取出来：握手阶段只负责提取，真正的 token/userId 匹配要调平台；校验通过前不能写注册表。
- 会话上限放在 registry 的 `compute` 里，和“查归属 + 绑定”一次原子完成，避免并发下先判断后创建导致超限。
- 同一用户重连仍然顶掉旧连接，是为了支持刷新页面；跨用户顶替则必须拒绝，否则 token 只能证明“已登录”，不能证明“这个 sessionId 属于你”。

**遗留**

- 未做单 IP 连接数限制；当前只有全局 session 上限。多租户或公网部署时建议在网关层按 IP 限速。
- token 仍走 query（浏览器 WS 不能设置 Header），会出现在代理/访问日志里；已有 `LogSanitizer` 和 Logback 兜底，但更彻底的做法是一次性短期 ticket。

**验收**：无 token / 无效 token 的 hello 被 1003 拒绝；query 与 hello 的 userId 不一致被拒；不同 userId 不能顶替 sessionId；会话数达到 `max-sessions` 后新 sessionId 被拒；11 个新增用例通过，上下文冒烟通过。

### SEC-10 CORS 与 WebSocket Origin 全开放

**位置**

- `src/main/java/com/hx/mcpsidecar/config/MyMvcConfig.java`（已删除）
- `src/main/java/com/hx/mcpsidecar/config/CorsConfig.java`（已删除）
- `src/main/java/com/hx/mcpsidecar/config/ws/WsConfig.java`
- 新增 `src/main/java/com/hx/mcpsidecar/config/ws/OriginHandshakeInterceptor.java`

**现状**

HTTP CORS 为 `allowedOriginPatterns("*") + allowCredentials(true)`，并重复注册了两份；
三个 WebSocket 端点均 `setAllowedOrigins("*")`。

**风险**

任意站点可携带用户凭证发起跨站请求/建立 WS；结合 query token 可被恶意页面利用。

**修复**

改为配置化的固定域名白名单；`allowCredentials(false)`；WS 校验 Origin，失败拒绝握手。

**修复记录（2026-11-17）**

**修改过程**

1. 确认实际调用形态：页面只通过 WebSocket 调用 sidecar，内网 Python Agent 是服务端调用，没有浏览器 HTTP 跨域需求，因此直接删除 `MyMvcConfig`、`CorsConfig` 两份通配 CORS 配置，HTTP 响应不再返回 `Access-Control-Allow-Origin`。
2. WebSocket 移除 `setAllowedOrigins("*")`，新增 `OriginHandshakeInterceptor`：
   - 无 `Origin`：放行（内网服务端 Agent），身份仍由 `/llm/*` 的 token 校验；
   - 与 sidecar 同主机、任意端口：放行（IP 部署时页面通常在同 IP 的另一端口）；
   - 其它主机：只允许 `security.allowed-origins` 中的来源；
   - 校验失败返回 403。
3. 配置 `application.yml` 新增 `security.allowed-origins: ${SECURITY_ALLOWED_ORIGINS:}`，默认留空，可在 `application-local.yml` / `application-server.yml` / `deploy` 配置中覆盖。
4. 发现 Spring 内置的 `OriginHandshakeInterceptor` 会先按完整同源（含端口）拦截，因此配置 `http://*:*` / `https://*:*` 让内置检查放行，实际来源校验由自定义拦截器完成，并保证它在链首。
5. 回归与端到端：
   - `OriginHandshakeInterceptorTest` 5 个用例 + `LogSanitizerTest` 4 个用例通过；
   - 恶意 Origin → 403；同 IP 不同端口 → 101；无 Origin → 101；
   - 白名单 `http://10.0.0.6:8080` → 101，未列入的 `http://10.0.0.7:8080` → 403；
   - `/ws/scene` 同样生效。

**核心逻辑**

- 修复目标不是“限制用户”，而是**限制哪些前端页面能借用户的浏览器建立连接**。`Origin` 是页面地址，不是客户端 IP，所以同主机任意端口放行，跨主机只认白名单。
- 不校验无 `Origin` 的请求，是因为内网 Python Agent 不是浏览器，本来就不会带 `Origin`；它们的身份由 token/内网边界负责。
- 删除 HTTP CORS 而不是加白名单，是因为当前没有浏览器 HTTP 调用；保留一份不用的 CORS 配置只会扩大误配置面。

**部署说明**

- 页面与 sidecar 同 IP 时无需配置；页面在其它 IP 时设置 `SECURITY_ALLOWED_ORIGINS=http://<页面IP>:<端口>`（多个用逗号分隔）。
- Docker 下 Compose 会自动读取根目录 `.env`，并已通过 `mcp-sidecar.environment` 的 `SECURITY_ALLOWED_ORIGINS` 映射注入容器；也可直接写挂载的 `application-server.yml`。

**验收**：非白名单 Origin 的 WS 握手被拒绝；同主机不同端口、无 Origin 的内网调用不受影响。

**位置**

**修改过程**

1. 新增 `utils/UrlUtils`：

   - `encodeQueryParam`：`application/x-www-form-urlencoded` 编码；

2. `AuthServiceImpl`：认证 URL 中的 `token` / `userId` 先编码再 `String.format`，防止 `&`、`#` 改变参数结构。
3. `ProxyWebSocketHandler`：转发到 Python Agent 的 `userId` / `sessionId` 作为路径段编码，`../` 不再能改变代理路径。

   - `PlatformInspectionMcp`：`type`；

   - `PlatformSecurityStatusMcp`：`date`。

   - 定向测试 22 个用例通过。

**核心逻辑**

- query 参数和路径段是两种不同的编码上下文：`&`/`=` 在 query 里会拆参数，`/`/`../` 在路径里会改层级。不能用同一种 `URLEncoder` 一把梭，所以工具里分成 `encodeQueryParam` 和 `encodePathSegment`。

### SEC-13 `LLMChatLimiter` 并发计数缺陷

**位置**：`src/main/java/com/hx/mcpsidecar/service/LLMChatLimiter.java:40-68`

**现状**：`tryAcquire` 与 `computeIfAbsent().incrementAndGet()` 非原子；`completeChat` 可能提前移除计数项。

**风险**：异常/并发路径下信号量泄漏，最终全局 10 个对话许可被耗尽，服务不可用。

**修复**：用 `ConcurrentHashMap.compute` 原子更新；`finally` 中释放；增加泄漏监控。

**修复记录（2026-11-17）**

**修改过程**

1. `connectedUserMap` 计数由 `AtomicInteger` 改为 `Integer`，所有增减/删除都放在 `ConcurrentHashMap.compute` / `computeIfPresent` 中完成。
2. `tryToChat`：先 `tryAcquire` 拿许可，再用 `compute` 原子登记用户计数；拿不到许可直接返回 false。
3. `completeChat`：`computeIfPresent` 内同时 `release()` 和递减，计数到 0 时同一次操作移除 key；并发调用只有一个线程能释放成功。
4. 回归：`LLMChatLimiterTest` 2 个用例通过：
   - 8 线程并发 `completeChat`，只有一个返回 true，信号量 availablePermits 保持 1；
   - 多会话按次数占用和归还。

**核心逻辑**

- 原实现的 `get()` → `release()` → `decrementAndGet()` → `remove()` 不是原子操作：两个线程可能同时读到同一个计数，各自 `release()`，把 1 个许可还成 2 个，长期会把限流上限放大。
- `ConcurrentHashMap.compute` 对同一个 key 串行执行，把“递减 + 判断归零 + 移除”合并为一次原子操作；`release()` 放在同一个 compute 里，保证一个计数只对应一次归还。
- 先拿许可再登记计数：如果获取许可失败，不能创建计数，否则后续 `completeChat` 会释放一个从未占用的许可。

**验收**：并发关闭不会重复释放；多会话计数正确归零。

### SEC-17 无 TLS / Spring Security 未启用

**位置**：`src/main/resources/application-server.yml:68-70`；`pom.xml:129-132`

**现状**：应用自身 `ssl.enabled: false`；Spring Security 依赖被注释，没有框架级默认拒绝。

**风险**：2222 直接暴露时，聊天内容与 query token 明文传输；新增接口默认裸奔。

**修复**：入口统一 TLS（Nginx/网关终止也可）；启用 Spring Security 并默认 `denyAll`，按需放行。

**风险接受记录（2026-11-17）**

部署形态：`agentic-app` 与 `mcp-sidecar` 在同一套 Docker Compose 内网运行，两者通过 `mcp-sidecar:2223` 通信（带 `MCP_API_KEY`）；`/llm/**`、`/ws/**`（2222）只给同内网的 Nginx 反向代理，2222 不发布到公网，宿主机外不可直接访问。

据此确认：

1. **外部攻击面**：公网只能到达 Nginx 的业务入口；sidecar 的 2222/2223 没有公网路由。
2. **明文范围**：仍存在 Nginx → 2222、sidecar → 平台后端两段 HTTP 明文，但都位于受控内网/同机 Docker 网络；能抓包的前提是已进入内网或取得宿主机权限。
3. **鉴权仍生效**：`/llm/**`、`/ws/**` 使用平台 token + userId 校验，`/mcp/**` 使用 `MCP_API_KEY`；TLS 缺失不影响“未授权调用”防护，只影响链路机密性。
4. **补偿措施**：2222 建议只绑 `127.0.0.1` 或由防火墙限制只允许 Nginx 来源；Nginx access log 使用不含 query 的 `log_format`，避免 `?token=` 落入日志。
5. **重新评估条件**：出现以下任一情况时本条恢复为待修——2222 需要直接暴露到办公网/公网；agent 与 sidecar 拆分到不可信主机；接入公网前端或第三方调用方。

**结论**：按“内网部署 + 网络边界”接受风险，不启用应用层 TLS，也不启用 Spring Security；上线评审需确认上述部署前提仍然成立。
