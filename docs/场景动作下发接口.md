# 场景动作下发 —— 请求格式速查

本文列的是**发一个动作到场景页面**的所有入口和 body 格式。三块内容：

| 入口 | 谁用 | 端口 | 鉴权 |
|---|---|---|---|
| [`POST /mcp/scene` → `tools/call`](#b-mcpscene--toolscall给-agent-用) | agent / LLM | **2223**（内网） | 无（端口隔离） |
| [`WS /ws/scene`](#c-ws-wsscene前端对接用) | 前端页面 | **2222**（公网） | 无 |

前者是**入口**（下发动作），后者是**出口**（动作帧到页面的样子）。
两者走的是同一条 `SceneDispatcher.dispatch` 链路，词表校验、破坏性闸门、
"页面没连就立刻失败"这些行为完全一致。

> `/mcp/**` 只监听内网端口 **2223**（server/local 一致；docker 只 expose 不 publish），
> 公网 **2222** 只开放 `/llm/**` 和 `/ws/**`。
> 系统全景与跨系统时序图见 [`系统架构说明.md`](./系统架构说明.md)。

## B. `/mcp/scene` → `tools/call`（给 agent 用）

### B1. 请求

```
POST http://mcp-sidecar:2223/mcp/scene   # 容器网络（内网）
#    http://127.0.0.1:2223/mcp/scene     # 本地调试
Content-Type: application/json
Accept: application/json, text/event-stream
mcp-session-id: <MCP 握手时服务端返回的>
X-Session-Id: dev-1                  ← 路由键，见下
```

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "scene_switch_floor",
    "arguments": { "floor": 3, "focus": true }
  }
}
```

### B2. 两个 session id 别搞混

| | 谁生成 | 作用 |
|---|---|---|
| `mcp-session-id` | **MCP SDK 自己生成**，`initialize` 时返回 | MCP 协议层的会话跟踪，跟业务无关 |
| `X-Session-Id` | **前端在 hello 里声明**，agent 原样注入 | 决定动作推给哪个页面 |

`X-Session-Id` 必须与前端 `hello` 里的 `sessionId` **逐字一致**，否则查不到连接。
**这个值绝不能由 LLM 填**（方案 §2.8）—— 由 agent 按用户身份注入。

<a id="sessionid-怎么填"></a>
### B3. `X-Session-Id` 缺失时的兜底

| 情况 | 行为 |
|---|---|
| 带了 header，命中连接 | 正常下发 |
| 带了 header，没命中 | ❌ 立刻报错"场景页面未连接" |
| 没带 header，**恰好 1 条**连接 | ⚠️ 路由到那一条（`scene.single-session-fallback=true`，默认开） |
| 没带 header，**2 条以上**连接 | ❌ 拒绝猜测，报错 |

兜底是给 Phase 1 单用户联调用的。**多用户上线前必须确认 agent 每个用户都带了 header**，
否则会推错浏览器。

### B4. MCP 工具的 arguments 写法

```json
{ "name": "scene_switch_floor", "arguments": { "floor": 3 } }
```

`arguments` 就是下表的字段。**没传的字段会被整条丢掉**（不是传 null），
前端用自己的默认值。

### B4b. 铺场约定：**不要重复下发 `ViewActor`**

前端执行器的**每条 `FocusTo` 前面都自己补了一条 `ViewActor`** 把目标显出来
（总览页自己不碰场景，用户对话时场景里可能什么都没有、也可能残留着上一个动作的图层），
重发是幂等的。这条在 `sceneExecutor.ts` 里记作"硬约束 5"。

**所以：**

| 想干的事 | 正确做法 | 错误做法 |
|---|---|---|
| 让某点位可见并聚焦 | 调 `scene_focus_actor` 或对应组合动作 | 先 `scene_set_actor_visible` 再 `focus_actor` |
| 看某路监控 | `scene_show_camera` | 先 `set_actor_visible` 铺场再 `show_camera` |

叠一次额外的 `set_actor_visible` 只会多发一条冗余帧 —— 不会出错，但没必要。
连 `scene_focus_actor` 本身也会让目标变可见（描述里已经写明）。

> 涉及的工具描述和后端实现见 `SceneActions` 类注释、
> `SceneMcp` 类注释，两处都写了这条。

### B6. 20 个工具逐个请求样例

先记住一件事：**下面每个 `params` 的内容，就是 MCP 的 `arguments` 内容。**
两边是同一个 map，只是外壳不同 —— 而且**工具名 == WS 动作名**（`TOOL_NAME_PREFIX = "scene_"`），
不用查映射表。

```jsonc
// 入口 A：MCP（给 agent）
{ "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": { "name": "<工具名>", "arguments": <下面的 params> } }

// 入口 B：联调（给人）
{ "action": "<工具名>", "sessionId": "dev-1", "params": <下面的 params> }
```

下面每段都对着运行中的服务实跑过。**没列出的键不要传**（传了 null 也会被丢掉）。

#### 楼层 / 视角

```jsonc
// scene_switch_floor —— 切换楼层
{ "floor": 3, "focus": true }          // floor✅ focus⬜

// scene_reset_view —— 重置视角到默认全景
{}

// scene_recover_view —— 恢复上一个视角
{}

// scene_close_detail —— 关闭业务弹窗并收回视角
{}

// scene_reset_all —— 全部重置：视角回楼栋全景 + 清 7 类专题图层 + 关弹窗
{}
```

#### 组合动作

```jsonc
// scene_show_visitor_track —— 访客轨迹
{ "floor": 1 }                          // floor⬜

// scene_show_camera —— 看某路监控
{ "tag": "CAM-3F-01",                   // tag✅ 摄像头点位标识（设备编号之类）
  "floor": 3,                           // floor⬜
  "app": "...", "stream": "...",        // ⬜ 原样透传，取值由前端定
  "name": "...", "source_url": "..." }  // ⬜ 同上

// scene_show_inspection —— 巡检 (目前是写死的,后续应该先寻路,再加上点位作为参数)
{ "floor": 1 }

// scene_show_meeting_rooms —— 会议室 (目前就切到某个楼栋某个楼层并显示会议室)
{ "floor": 3 }

// scene_show_dining —— 食堂
{ "floor": 1 }                          // floor⬜

// scene_show_area_overview —— 防区总览
{ "floor": 99, "tags": ["A1", "A2"] }   // tags⬜ 要高亮的防区标识列表

// scene_show_device_category —— 按设备类目显示点位
{ "category": "JIANKONG", "floor": 3 }  // category✅ 类目名

// scene_show_fusion —— 虚实融合视频
{ "tag": "FUSE-01",                     // tag✅
  "build": "...", "floorNum": 13,       // ⬜
  "options": "..." }                    // ⬜ 原样透传
```

> **楼层值 11 和 99 都是"楼栋视图"** —— 前端 `useSplitBuild` 以 `>=11` 判定，
> 所以 `scene_show_area_overview` 的"默认 11（整栋楼）"和 `FLOOR_SEMANTICS` 的
> "99=整栋楼"**都对，不矛盾**。差别只在 `FloorSelecter` 的高亮：它拿 `appState.floor`
> 与那 11 项比对，11 命中所以"楼栋"按钮呈选中态，99 匹配不上所以全不高亮 ——
> `scene_reset_all` 用 99 就是为了清场时看不出选中了哪层。

#### 原子动作

```jsonc
// scene_focus_actor —— 相机聚焦到某对象（会先铺 ViewActor，所以目标会变可见）
{ "actorType": "POI",                   // actorType✅ 如 BASEACTOR/POI/AREA
  "type": "JIANKONG",                   // type✅      如 JIANKONG/MEETING_ROOM
  "tag": "CAM-3F-01" }                  // tag✅

// scene_set_actor_visible —— 显示/隐藏某个对象
{ "actorType": "POI", "type": "JIANKONG", "tag": "CAM-3F-01",
  "visible": true }                     // visible✅ true=显示 false=隐藏

// scene_set_poi_visible —— 显示某类 POI / 隐藏全部 POI
{ "type": "JIANKONG", "build": "科研办公楼", "floorNum": 3,
  "visible": true }                     // 显示某一类
// 隐藏全部 POI 时这三个用不上，但 schema 标了必填 → 见下方注意事项

// scene_set_env —— 环境时间/天气
{ "env_time": "夜晚" }                   // 至少填一个，见下方注意事项
{ "env_weather": "雨" }
{ "env_time": "傍晚", "env_weather": "雪" }   // 两个一起也行
```

#### 破坏性动作（当前被挡）

```jsonc
// scene_set_area_state —— 设置防区状态
{ "tag": "A1", "state": "撤防" }         // state✅ 离线|布防|撤防|告警

// scene_set_inspection_state —— 控制巡检任务
{ "tag": "INS-01", "state": "开始" }     // state✅ 开始|暂停|结束
```

现在（`scene.destructive-enabled=false`）这两个一律返回 409：

```json
{ "ok": false, "state": "rejected",
  "error": "该动作会改变现场状态，需要用户确认后才执行，当前阶段尚未开放" }
```

等 Phase 4 接上确认卡片后才放行。

#### 查询类

```jsonc
// get_scene_state —— 读页面状态快照，不下发动作
{}
```

这个不走 dispatch，只读缓存，只能通过 MCP `tools/call` 调。返回类似：

```json
{ "type": "scene_state", "sessionId": "dev-1", "ready": true,
  "floor": 3, "build": "科研办公楼" }
```

### B7. 三个参数上的注意事项

**1. `scene_set_poi_visible` 的 schema 要求过头了** ⚠️

四个参数在 schema 里**全是必填**，但 `type`/`build`/`floorNum` 只在 `visible=true` 时用。
想隐藏全部 POI 时，模型被迫给这三个用不上的参数编值。建议给它们加 `required = false`。

**2. `scene_set_env` 反着来**

schema 里两个都选填，运行时却要求至少填一个。靠返回值报错兜着，问题不大：

```
调用 scene_set_env 失败：env_time 和 env_weather 至少要填一个。
```

**3. 中文状态值写错会被静默忽略**

`state` 的取值在 schema 里是 enum 约束的（`离线|布防|撤防|告警`），
传 ASCII 值会在协议层就被挡下：

```
No enum constant com.hx.mcpsidecar.scene.SceneActions.AreaState.armed
```

之所以要这么严，是因为**写错的中文值 UE 不报错，只是当没收到**。

## C. WS `/ws/scene`（前端对接用）

```
ws://127.0.0.1:2222/ws/scene
```

入站帧用 `type` 区分，出站帧用 `event`/`data` —— 这个不对称是协议原文如此。

### C1. 页面 → sidecar

**① 连接后必须先打招呼**，否则其他帧一律被忽略：

```json
{ "type": "hello", "sessionId": "dev-1", "userId": "u-42" }
```

`sessionId` 空 → 服务端直接关连接。同一 `sessionId` 再连，**新连接顶掉旧连接**
（旧 socket 被服务端关闭），在途动作会重发给新连接。

**② 状态快照**（覆盖式缓存，不解析不校验）：

```json
{
  "type": "scene_state", "sessionId": "dev-1", "ready": true,
  "floor": 11, "build": "科研办公楼"
}
```

**③ 动作回执**（兑现挂起的工具调用）：

```json
{
  "type": "action_result", "sessionId": "dev-1",
  "actionId": "a-7c21", "state": "dispatched",
  "durationMs": 120, "error": null
}
```

| `state` | 含义 |
|---|---|
| `dispatched` | 正常，已执行 |
| `rejected` | 拒绝，**必须带 `error`** |
| `awaiting_confirm` | Phase 4 用，当前不会出现 |

`error` 约定：

| 值 | 含义 |
|---|---|
| `UNKNOWN_ACTION:<name>` | 词表不同步，前端不认识这个动作 |
| `BAD_PARAM:<key>` | 缺参数，`key` 必须原样给（模型靠它自我纠正） |
| `BAD_FRAME` | 帧缺 `actionId` 或 `name` |
| `PLAYER_NOT_READY` | 播放器没就绪 |

`actionId` 是唯一的关联键，**必须原样回传**。收到不认识的 `actionId` 直接丢回执
（超时后的迟到回执），服务端不报错。

**④ `action_confirm`** —— Phase 4 才用，当前前端不用产生。

### C2. sidecar → 页面

```json
{
  "event": "action",
  "data": {
    "actionId": "a-7c21",
    "sessionId": "dev-1",
    "name": "scene_switch_floor",
    "params": { "floor": 3, "focus": true }
  }
}
```

`params` 里**不会有 null**，没传的参数键直接不存在，前端用自己的默认值。
前端执行器**不做去重，收到就执行**（所以重连重发是协议允许的，代价见下）。

## 坑

**1. `415 Unsupported Media Type`**
`POST /mcp/scene` 要求 `Content-Type: application/json`。
curl `-d` 默认发 `application/x-www-form-urlencoded`；Postman 默认是 Text。
→ 加 header。

**2. `409` 优先怀疑 sessionId**
"场景页面未连接"九成是 `sessionId` 填得和前端 `hello` 里的不一致，
或者前端压根没连。先确认页面已经发过 `hello`。

**3. 字段名不匹配会静默丢帧**
`sessionId` / `actionId` / `type` / `event` / `params` 这些键写错，服务端**不报错**，
只打一条 warn 日志然后忽略。联调时对不上先看服务端日志。

**4. 动作超时（15s）不代表没执行**
帧可能已发出、只是回执丢了，也可能还卡在缓冲区。超时返回的是
"执行状态未知"，别当成"没执行"。
